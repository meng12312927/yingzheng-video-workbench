# PRD：映证｜活动视频需求与审核工作台

> 版本：v3.4
> 状态：MVP2 已实现，进入真实用户假设验证阶段
> 更新日期：2026-07-16
> 产品定位：面向学校和企业活动团队的低门槛视频需求、审核与验收工作台

## 1. 产品概述

### 1.1 一句话定位

活动视频太长、负责人要求又说不清？映证帮你找出该剪的内容，生成有证据可查的粗剪方案，负责人确认后再导出。

### 1.2 核心价值

产品不与剪映、FastCut、Premiere、After Effects 等软件竞争完整时间线、特效或专业渲染能力，而是解决剪辑软件上游和交付环节的问题：

> **剪映解决“怎么剪”，映证解决“剪哪里”和“剪完谁点头”。**

- 剪之前把要求说清楚，减少模型和剪辑人员自行猜测。
- 剪的时候说明为什么选择每个片段，避免遗漏关键人物和环节。
- 导出前让负责人低门槛审核，不要求其学习专业剪辑软件。
- 修改过程有业务记录，能够追溯谁修改、批准了什么。
- 交付时逐条检查需求是否满足，降低反复返工。

产品的核心链路是：

```text
模糊需求
  → 结构化任务书
  → 用户确认
  → 素材分析与证据提取
  → 有依据的候选片段
  → 电脑端方案审核
  → 确认后的剪辑计划
  → 基础成片输出
  → 逐项验收与交付报告
```

### 1.3 产品原则

- **低门槛**：用户只需描述活动、选择重点并审核候选，不需要理解时间线、MCP、Agent 或提示词工程。
- **少打断的人工审核**：AI 判断先以建议草稿呈现，但只在需求有关键歧义、高风险信息或最终方案需要业务选择时要求用户决策；通过的系统检查自动继续。
- **先确认后执行**：未经确认的需求、风格、片段和时间线不得进入正式渲染。
- **证据优先**：模型结论必须尽可能引用转录、时间范围或用户标注，不展示不可验证的内部推理。
- **人机协作**：人名、职务、奖项和必须内容等高风险信息由用户确认。
- **执行器可替换**：当前使用 FFmpeg；未来可以接入外部剪辑软件，但不是 MVP 的前置条件。
- **本地优先**：原始音视频默认在本机处理；MVP 的审核也在本机电脑端完成。
- **渐进增强**：MVP 先验证“需求是否说清、重点是否找准、审核是否省时”；组织记忆、多模态证据、私有化模型和分布式基础设施只有在前述假设成立后再引入，不能用技术复杂度替代用户价值。

## 2. 目标用户与角色

### 2.1 服务对象

- 学校宣传部门、校园融媒体团队。
- 企业行政、市场、新媒体与活动执行团队。
- 为学校和企业服务的小型视频工作室。

### 2.2 直接操作者

- 学校宣传老师、校园融媒体学生。
- 企业新媒体运营、年轻行政人员、活动执行人员。
- 会使用手机或电脑版剪映，但不擅长从长素材中快速找重点的轻中度剪辑用户。

### 2.3 审核者

- 学校领导、活动负责人、企业负责人、客户或宣传部门负责人。
- 审核者不需要学习时间线；MVP 通过电脑端审核页查看任务书、候选片段和成片。

### 2.4 核心用户特征

- 原始素材通常为 30 分钟至数小时。
- 成片用于公众号、内部汇报、活动回顾或正式宣传。
- 存在必须覆盖的人物、发言、环节、奖项或产品信息。
- 目前使用剪映等工具，但在找片段、改字幕、等待审核和反复返工上耗时明显。
- 没有稳定的专业后期团队，或剪辑者与审核者不是同一个人。

### 2.5 非目标用户

- 只制作几十秒日常短视频的个人用户。
- 追求高度原创视觉表达的专业导演和大型后期团队。
- 需要复杂多机位、电影级调色或声音设计的项目。
- 希望一句话完全无人审核生成最终成片的用户。

## 3. 核心场景

### 3.0 两个角色的任务故事

**操作者：小张，校园融媒体学生。** 周五下午，她拿到两小时运动会素材，领导只说“周一早上发，要有开幕、冲刺和颁奖”。小张上传素材，补充用途与必须内容；映证转录后给出带依据的候选和粗剪方案。她删掉无关片段，并把三个学生姓名标为“待确认”，将审核链接发给李主任。

**审核者：李主任，学校宣传负责人。** 周六早上，他在电脑审核页只看需要他决定的内容：删掉两段自己的讲话、确认三个人名，并留言“多保留颁奖”。确认后，小张得到新的方案并导出。李主任不需要学习时间线，也不需要逐项点击八次“确认”。手机链接是验证电脑端闭环后才做的 V1.1 能力。

### 3.1 学校活动

- 运动会、开学典礼、毕业典礼、文艺汇演、校园比赛和颁奖活动。
- 重点核对学校名称、班级、师生姓名、领导职务、奖项和未成年人隐私。

示例需求：

> 将一小时运动会录像制作成三分钟公众号回顾视频，必须包含开幕、短跑冲刺、集体项目和颁奖。领导讲话只保留核心内容，使用中文字幕，涉及学生姓名时先让我确认。

### 3.2 企业活动

- 年会、培训、发布会、会议、团建、签约和产品演示。
- 重点核对品牌规范、发言人、职务、产品名称、合作伙伴和对外发布限制。

示例需求：

> 将企业发布会剪成五分钟正式回顾，必须包含产品亮相、客户评价和签约环节。CEO 发言保留核心句，使用企业标准片头，合作伙伴名称必须人工确认。

### 3.3 MVP 场景配置策略

学校和企业的差异在 MVP 中采用一份可查看、可测试的配置表管理，包括场景关键词、必须人工核对的信息和隐私提示。当前不拆分 `school.py`、`enterprise.py` 等独立领域包，因为每个场景只有少量验证任务，尚不足以证明需要两套不同的领域逻辑。

首轮真实任务只验证以下差异：

| 场景 | 辅助关键词 | 必须核对 | 隐私或发布风险 |
| --- | --- | --- | --- |
| 学校 | 班级、年级、班主任、校长、奖项 | 师生姓名、奖项名称、领导职务 | 未成年人信息和肖像 |
| 企业 | 产品、客户、合作伙伴、发言人、发布会 | 发言人职务、产品名称、合作伙伴 | 商业信息和对外发布限制 |

配置只用于补充追问、检索词和风险提示，不能替代用户任务书，也不能把配置中的词自动升级为 `must`。只有真实评测证明两个场景形成稳定且复杂的差异后，才考虑拆分独立领域模块。

## 4. 核心功能

### 4.0 阶段性审核工作流

产品采用“系统自动检查 + 关键决策才请人确认”的工作流，而非由 AI 连续自动做完所有决定，也不是让用户逐项点击八次“确认”。每个 AI 判断必须显示其输入、建议结果、依据、风险和可执行操作。

| 阶段 | 默认行为 | 何时需要用户操作 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 素材预检 | 自动记录时长、分辨率、音视频流和风险 | 仅在预检失败或风险较高时替换素材/终止 | 预检通过后自动继续；失败不能绕过 |
| 需求编译 | 自动生成任务书草稿与执行说明 | 仅在缺少关键业务信息、存在 `must`/禁止项或高风险名称时回答、编辑并确认 | 关键歧义消除后确认需求版本 |
| 素材—需求对齐 | 任务书确认前生成转录与素材摘要，比较素材事实和初步任务书 | 仅在需求过宽或与素材明显错位时采用建议、修改后采用或保持原要求 | 用户明确处理建议；建议不能静默写入任务书 |
| 风格推荐 | 用户选择学校/企业场景且任务书确认后，LLM 自动从已有样式库推荐最多 3 组并说明理由 | 用户可在方案审核页选择、替换或忽略；推荐不强制采用 | 没有可用推荐或用户忽略时使用基础样式，不产生独立审核页 |
| 证据分析 | 自动生成转录和证据范围 | 仅当转录影响 `must` 项、人名/奖项或模型标高风险时修正/标注 | 无高风险自动继续；有风险并入方案审核 |
| 候选与时间线 | 自动生成候选、理由、预览和粗剪时间线 | 在**同一个方案审核页**保留/删除/排序/修正文字、处理风险并批准 | 这是 MVP 的主要人工决策 Gate |
| 渲染前检查 | 自动核对将执行的版本、时长和输出设置 | 用户点击“导出”即确认渲染；有失败项只能返回修改 | 检查通过且点击导出后渲染 |
| 成片验收 | 自动生成逐项报告 | 仅当存在 warning、failed 或需人工确认项时选择修订或接受例外 | 无异常自动归档；有异常后由负责人决定 |

MVP 的显式人工决策最多为三处：必要时确认需求、审核候选与时间线、处理交付异常；“导出”是动作确认而不是额外审批页。确定性系统动作（如时间范围校验、时长重算、文件检查）展示结果和失败原因，但不要求逐项审批，也不能被绕过。

PRD 的唯一状态语义如下。只有系统确实暂停并等待用户输入时才使用 `awaiting_*`；自动处理、自动通过和可跳过步骤均使用完成态或进行态：

```text
created
  → preflight_ok
  → requirement_draft
  → awaiting_requirement_clarification   （条件状态：仅有关键歧义时进入）
  → requirement_confirmed                （无歧义时可在任务书页直接继续）
  → style_recommended / style_skipped    （自动，不增加审批）
  → analyzing
  → awaiting_review                      （候选、证据和时间线合并审核）
  → plan_approved
  → rendering
  → verifying
  → awaiting_delivery_resolution         （条件状态：仅有交付异常时进入）
  → succeeded

任意不可恢复错误 → failed
已批准方案被修改 → 旧批准失效 → awaiting_review
awaiting_delivery_resolution 选择返回修订 → 旧交付报告保留 → awaiting_review
```

因此 MVP 最多只有三个可能的人工作业点：`awaiting_requirement_clarification`、`awaiting_review` 和 `awaiting_delivery_resolution`。`plan_approved` 是方案审核的结果，不是第二次方案审批；`rendering` 由用户点击“导出”触发，但不再出现单独的渲染确认页。

上述状态不是 UI 展示标签，而是任务的唯一业务状态。任何推进、回退、重试和恢复都必须由“当前状态 + 业务事件 + 前置条件”驱动；重复提交同一事件不能产生重复渲染或重复审批。MVP 至少验证非法跳转被拒绝、已批准方案修改后回到 `awaiting_review`、失败后保留已完成产物以及任务重新打开后能够恢复当前状态。

### 4.1 需求编译与确认

系统将自然语言转为用户可见、可修改的结构化任务书：

- 视频用途、目标受众和发布渠道。
- 目标时长及允许误差。
- 画幅、风格和节奏。
- 必须、应该、可选和禁止内容。
- 人物、职务、奖项、产品和组织名称。
- 字幕、BGM、片头片尾及品牌要求。
- 隐私和对外发布限制。
- 可执行的验收条件。
- 无法确定、等待用户确认的信息。

独立的需求澄清 Agent 根据原始描述、任务书草稿和槽位状态，动态提出最多 3 个真正影响成片的问题。每个问题都展示提问原因和可能影响，并允许用户补充或暂时忽略；用户确认后固化一个不可静默修改的需求版本。

### 4.1.1 风格推荐与选择

片头、片尾、字幕和转场样式不能只由 AI 用自由文本描述，也不能让模型临时编造当前渲染器不支持的效果。系统应维护一个可预览、可版本化的样式库，AI 只从库中提出少量与任务书匹配的建议，用户筛选或确认后才写入交付规则。

样式库的来源按优先级为：

1. 组织品牌模板：学校或企业已确认的 Logo、色彩、字体、片头片尾和字幕规范。
2. 活动场景模板：正式活动回顾、热烈运动会、企业发布会、培训纪要等。
3. 通用基础样式：当前 FFmpeg 已实现的经典/简洁/醒目字幕、硬切/淡转场、标题卡/黑场淡入淡出。

触发条件固定为：用户已经选择学校或企业场景，并且任务书版本已经确认。满足条件后，LLM 根据活动用途、受众、风格要求、目标时长和内容节奏，从当前执行器支持的样式库中最多推荐 3 组组合方案；每组包含全局片头、片尾、字幕和默认转场，并说明与本次任务书的匹配原因。

风格建议只作为候选与时间线审核页的一部分，不新增 `awaiting_style_confirmation` 或独立审批页。用户可预览、选择、关闭某项、逐项替换或完全忽略建议；未选择时继续使用基础样式。模型只能返回样式库中的稳定 ID，不能自由生成执行器不支持的特效名。LLM 不可用时跳过推荐，不阻断证据分析。

### 4.1.2 用户可见的 AI 执行说明

系统在生成需求任务书草稿时同步生成一份用户可查看、可编辑的 **AI 执行说明**。它与任务书显示在同一页面、绑定同一需求版本，并在同一次需求确认中固化，不新增“再次确认执行说明”的人工决策。它不是暴露内部系统 Prompt，而是说明 AI 将如何依据需求和证据完成本次任务。

执行说明至少包含：

- 本次成片的用途、受众、目标时长和允许误差。
- 必须、应该、可选和禁止内容。
- 已确认的风格、画幅、字幕样式、BGM、全局片头片尾和默认转场。
- 每个必须内容的覆盖规则。
- 本次允许使用的证据范围，例如转录片段、用户标注或已确认的人物信息。
- 需要模型输出的候选字段：源时间、证据、入选原因、风险提示和建议时长。
- 需要人工确认的高风险信息，例如人名、职务、奖项和视觉风格。

用户看到的是业务语言，例如“颁奖必须出现，并引用转录证据”；系统内部的安全规则、工具 Schema、密钥、路径和隐藏推理不展示。每份执行说明与需求版本绑定，确认后不能被后续模型调用静默替换。

### 4.1.3 多轮结构化澄清

需求澄清不是无边界闲聊，而是围绕任务书缺失项和冲突项进行的有限多轮 Form-filling。需求澄清 Agent 每轮读取原始需求、当前任务书和允许询问的槽位，只生成真正影响选段、合规或验收的 0–3 个问题，并同步更新可见任务书。问题不是固定模板，每个问题必须绑定现有槽位，同时说明“为什么问”和“不补充可能影响什么”。

每个被提取的需求值至少标记以下状态：用户明确提供、模型建议、待确认、已确认或存在冲突，并保留来源消息。模型推断不得静默覆盖用户已确认值；用户修改时生成新任务书版本，并使依赖旧版本的候选、计划和批准失效。

澄清过程必须满足：

- 已经明确的信息不重复询问；用户说“不确定”时保留未知状态，不自动补默认事实。
- 用户可暂时忽略非冲突问题；被忽略的高风险信息保持未知状态，并在候选审核和成片验收中继续提示人工复核。
- 用户前后描述冲突时并列展示来源和差异，由用户选择或改写，不能由模型自行裁决。
- 最近对话、已确认任务书和当前缺失槽位构成最小上下文；不把全部历史消息无限追加到 Prompt。
- 澄清完成的判定由任务书完整性和业务规则决定，而不是由模型自由宣布。
- 模型只能提出问题，不能直接修改任务书值；问题数量、允许槽位、重复项和输出格式均由 Harness 校验。
- AI 澄清调用失败时明确显示失败，不使用固定问题冒充 AI 结果，用户仍可直接编辑任务书。

### 4.1.4 素材—需求对齐

系统在最终任务书确认前完成一次素材预分析：复用本地 Whisper 生成转录和证据窗口，由 `RequirementAlignmentAgent` 比较原始需求、初步任务书与素材摘录。模型只能输出 `aligned`、`too_vague` 或 `mismatch` 建议，不能直接修改任务书。

当需求过宽或与素材错位时，页面必须展示素材摘要、识别主题、调整原因、建议用途、建议时长和可验收的重点内容，并提供“采用建议”“修改后采用”“保持原任务书”三种操作。用户处理后生成新任务书版本和审计事件，再运行动态澄清 Agent。预分析转录保存为任务产物，正式候选分析必须复用，不能再次运行 Whisper。

### 4.2 素材分析与候选证据

- Faster-Whisper 在本机生成带源时间戳的中文转录。
- LLM 根据已确认任务书识别候选片段，而不是只做泛化“高光”判断。
- 系统先用 BM25 和 Embedding 两路检索为每条需求召回带时间戳的转录证据，再以 RRF 融合排序；LLM 只能在该受限证据集上生成候选。
- 采用混合检索是因为 BM25 更擅长精确命中人名、奖项名称、产品名和活动环节等中文专有词，Embedding 更擅长覆盖“冲刺”与“冲向终点”这类措辞不同但语义接近的内容。RRF 使用名次而非直接混合两种不可比的原始分数，使任一路排名靠前的证据都不会轻易丢失。
- 每个候选片段关联具体需求、稳定证据 ID、原文引用、入选原因、置信度、建议时长和风险提示；不能只返回自由文本理由。
- 候选按任务书要求分批生成，单批最多返回 2 个紧凑选择；模型只建议证据 ID、源时间、理由和置信度，原文引用、需求关联与检索分数由代码从当前证据范围确定性补齐。某项失败只重试和隔离该项，不得使其他成功需求整体降级，也不得把该项规则候选混入可出片集合。
- 代码先对引文和证据执行 Unicode NFKC 归一化，并忽略空白与标点差异，再验证引文仍是证据原文的连续子串；同时验证证据时间包含于候选范围、需求 ID 有效及 `must` 覆盖情况。该规则允许 LLM 调整引号、逗号和断句，但不允许改写实体字符。
- MVP 不采用“编辑距离 5% 即视为有效证据”的字符级模糊通过规则：短中文人名或“一等奖/二等奖”只差一个字，模糊匹配可能把错误实体当作原文。字符发生变化的引用标记为需重新复制原文或人工复核，不能作为自动选段的有效证据。语义相关性仍由检索和受限 LLM 提供建议，不伪装成代码证明。
- 候选必须落在合法素材时间范围内，由确定性代码吸附到完整 ASR 片段边界、补齐明显承接句，并完成跨需求去重、合并、时长和重叠检查。
- 第一阶段以转录证据为主；后续扩展 OCR、场景切换、响度、人物线索和用户标注。
- 用户在候选生成前可以查看、修正、排除或补充证据；系统只使用当前已确认的证据范围进行分析。
- 候选总时长低于任务书最低值时，审核页必须同时提供两条清晰路径：用户可明确接受当前短版并留下计划级例外记录，或直接播放原素材、拖动选段范围并勾选对应任务书要求来补入片段。时长例外只豁免 `plan_duration_too_short`，不能绕过必须项覆盖、证据、素材边界或禁止内容检查。

### 4.2.1 活动辅助资料与多源证据

视频仍是任务的主素材；活动流程表、主持稿、人物与职务名单、奖项名单、产品资料和组织品牌规范是可选辅助资料，用于核对专有名词、扩展检索词和判断候选覆盖，不把产品扩展为通用企业知识库。

辅助资料中的事实必须保留文件、页码或条目位置和版本。外部资料与视频内容冲突时标记为风险，不得直接改写视频原文；只有用户确认后的姓名、职务、奖项和品牌文字才能进入正式字幕或标题。

MVP 2 仍以转录证据和用户标注为主；V1.1 在真实任务证明“专有名词核对”是主要返工来源后支持小规模活动辅助资料；V1.2 再按收益增加 OCR、场景切换、音频事件、关键帧描述和人物线索。所有证据类型复用稳定 ID、源位置、置信度、确认状态和引用校验机制。

### 4.2.2 检索融合与候选重排

召回负责尽量不漏掉 `must` 内容，重排负责把更相关、更完整、质量更高且风险更低的证据和片段排在前面。候选重排可以综合需求相关性、上下文完整度、音画质量、重复度、风险和人工确认状态，但只影响建议顺序，不自动决定最终入选集合。

引入任何 Rerank 模型前必须用同一标注集对比 BM25、Embedding、RRF 与 RRF + Rerank，至少记录 `must` Recall@K、MRR/NDCG、人工删除率、延迟和降级结果。没有稳定提升时保留当前更简单的检索链路。

### 4.3 可审核剪辑方案

每个候选片段展示：

- 源视频起止时间与低码率预览。
- 对应的需求编号和优先级。
- 入选原因与引用证据。
- 置信度及待确认信息。
- 保留、删除、字幕修正、缩短、延长、替换、排序和补充人工片段操作。

AI 的重要性评分和建议时长只用于排序，不会自动决定最终入选集合。用户确认候选集合后，系统重新计算时间线和字幕，不复用旧结果。

### 4.3.1 可审核时间线规格

最终方案不仅是一组“保留片段”，还必须生成用户可审阅的时间线规格。它将“要剪什么”和“怎样呈现”分开：

- **全局交付规则**：总时长、画幅、帧率、字幕开关与样式、BGM、全局片头片尾、默认转场和输出格式。
- **片段规则**：每段的源视频开始/结束时间、预计成片开始/结束时间、对应需求和证据、片段标题、字幕范围、是否添加片段标题卡、片段后的转场和时长。
- **边界规则**：相邻片段是硬切、淡转场还是其他预设；转场时长从成片总时长中扣除。

默认情况下，只有全局片头和片尾；“每个小片段的片头”作为可选的片段标题卡，必须由用户或模板明确启用，避免活动回顾被过多标题卡打断。

AI 可以对某些边界建议更强或更弱的转场、对某些片段建议标题卡，但必须引用明确的节奏或内容原因，例如“开幕式进入比赛主体”或“从领导讲话转入颁奖”。用户在时间线中逐条接受、替换或关闭；未确认的局部风格建议不会进入渲染计划。

用户应能查看类似如下的计划：

| 成片时间 | 源视频时间 | 内容与依据 | 呈现方式 |
| --- | --- | --- | --- |
| 00:00–00:02 | — | 全局片头 | 学校标题卡，2 秒 |
| 00:02–00:17 | 00:01:12–00:01:27 | REQ-001 开幕式；引用主持人宣布开幕 | 经典字幕；片段标题“开幕式”；0.35 秒淡转场 |
| 00:16.65–00:31.65 | 00:18:20–00:18:35 | REQ-002 短跑冲刺；引用转录证据 | 经典字幕；无标题卡；0.35 秒淡转场 |
| 00:31.30–00:46.30 | 00:42:15–00:42:30 | REQ-003 颁奖；引用“下面进行一等奖颁奖” | 经典字幕；片段标题“颁奖时刻” |

时间线在用户确认后固化为计划版本；任何时长、字幕、标题卡或转场修改都会生成新版本并使旧批准失效。

### 4.4 MVP 审核范围

MVP 只实现电脑端审核：编辑任务书、查看证据与候选预览、处理高风险文本、选择片段并导出。核心任务事件和本机审批必须具备幂等保护；局域网、二维码、移动 token、过期、撤销和跨设备重复提交保护属于 V1.1，它们不能挤占证据检索、校验和评测的开发时间。

### 4.5 业务审计记录

记录用户可理解的业务事件：

- 原始需求提交。
- AI 生成任务书。
- 用户修改和确认需求。
- 系统生成候选片段。
- 用户删除、保留或修正内容。
- 审核者批准方案。
- 系统渲染、验收和生成修订版。

业务审计记录与底层技术日志分开：

- `audit_log`：面向用户的业务记录。
- `system_log`：面向开发和故障排查的技术记录。

### 4.5.1 任务记忆与组织记忆

Memory 只保存能够减少重复说明和返工的已确认信息，不保存模型隐藏推理，也不把未确认推断自动升级为长期事实。

- **任务记忆（MVP 2）**：当前需求版本、已确认槽位、证据范围、候选取舍、审核意见、计划版本和交付异常，用于任务恢复和局部重新分析。
- **组织记忆（V1.1）**：经组织管理员确认的品牌模板、常用组织名称、人物与职务词典、奖项/产品词典和发布限制；每条内容可查看来源、版本、有效期并可删除。
- **偏好记忆（V1.2 候选项）**：从多次明确选择中形成的字幕、节奏或讲话保留偏好，只作为下一任务的可见建议，不能自动成为 `must` 或绕过审核。

需求变更时优先读取当前任务已确认信息；组织记忆只补充候选和追问，不得覆盖任务书。敏感个人信息遵循最小保存、可撤销和可删除原则。

### 4.6 渲染与交付

- 当前使用 FFmpeg 完成裁剪、拼接、淡转场、BGM、片头片尾和字幕烧录。
- 输出 H.264/AAC MP4；macOS 优先 VideoToolbox，失败时回退 `libx264`。
- 渲染器是可替换执行层。Premiere、Resolve、AE 或 FastCut 等外部适配不属于当前核心范围。

### 4.7 逐项验收

系统依据已确认任务书生成验收报告：

- 代码验证：文件可解析、音视频流、时长范围、字幕存在、片段覆盖、确认状态。
- 语义验证：必须环节是否由已确认候选覆盖，人物或奖项是否仍有未确认项。
- 无法可靠自动验证的项目标记为“需人工确认”，不得伪装为通过。

语义验收由 AI 提供时，只能给出“建议通过/需复核/可能不满足”及其证据，不能自动宣告最终交付。用户必须对存在 `warning`、`failed` 或“需人工确认”的报告选择“返回修订”或“接受例外并批准交付”。

示例：

```text
✓ 成片时长在 165–195 秒之间
✓ 已包含开幕式
✓ 已包含颁奖环节
✓ 使用了确认后的领导姓名与职务
△ 产品演示片段短于任务书建议时长
✗ 企业标准片尾尚未配置
```

### 4.7.1 输出合规与发布风险

系统把合规检查纳入任务书、候选审核和交付验收，而不是仅在最终 Prompt 中增加一句“注意安全”。学校场景重点检查未成年人信息、姓名、奖项和领导职务；企业场景重点检查产品名、合作伙伴、未公开信息和对外发布限制。

确定性规则负责检查确认状态、禁止项覆盖、版本绑定和发布权限；模型只能提示疑似隐私、实体错误或不适合公开的内容，并返回 `needs_review` 或 `possible_violation` 及证据。未经确认的高风险文字不能进入正式字幕、标题或对外发布成片；用户接受例外时必须留下原因和批准记录。

## 5. 当前已实现基础

- 一段或多段视频的媒体预检；多段素材统一规格后按上传顺序合成为一条长视频，并保存原素材顺序和时间偏移映射。
- 本地中文转录和基于转录的候选分析。
- 候选时长范围校验、去重和目标时长控制。
- 候选低分辨率预览和用户勾选确认。
- 字幕校对及成片时间轴重映射。
- BGM、淡转场、字幕样式、基础片头片尾。
- FFmpeg 渲染、VideoToolbox 回退和最终媒体校验。
- 每个任务的 JSON、SRT、日志和成片产物归档。

当前 MVP2 已完成结构化任务书与有限多轮澄清、显式状态机和任务恢复、受控风格推荐、转录证据窗口、BM25/向量混合检索、受限证据工具调用、候选引文校验、可审计时间线、计划批准门禁、FFmpeg 执行、逐项交付报告、业务审计和 6 个标注任务的离线对比评测。模型需求解析失败时保留原始输入并进入显式人工核对草稿，不会静默生成默认正式需求。手机审批、外部剪辑器适配和真实用户评测仍不属于 MVP2。

## 6. MVP 2 验收标准

| 类别 | 验收标准 |
| --- | --- |
| 需求编译 | 原始需求可生成结构化任务书；用户可修改并确认；必须/应该/可选/禁止内容区分明确 |
| AI 动态澄清 | 只围绕允许的缺失、推断或冲突槽位动态追问；每次编译最多提出 3 个带原因与影响说明的问题；已明确或已忽略的信息不重复询问 |
| 状态机 | 非法跳转被拒绝；重复事件不产生重复副作用；批准后修改会使旧 Gate 失效；任务重新打开后能恢复当前状态 |
| 证据链 | 每个 AI 候选至少关联一条需求、稳定证据 ID 与可校验原文引用；无证据候选不得进入自动选段 |
| 工具调用 | 候选分析通过受限 `search_evidence` 工具检索证据；模型不能读取未授权的全文转录 |
| 审核 | 未批准方案不能渲染；用户修改后重新生成确认计划和字幕时间线 |
| 电脑审核 | 操作者可在同一页面查看任务书、证据、候选和时间线，并提交选择与修正 |
| 审计 | 需求修改、片段选择、文字修正、批准和渲染均形成业务事件 |
| 验收 | 最终输出生成逐项报告；代码可验证项不得只依赖 LLM 判断 |
| 隐私 | 默认不上传原始音视频；转录、预览和任务产物保留在本地任务目录 |
| 评测 | 至少有 6 个标注任务；产出 `must` Recall@K、MRR/NDCG、证据引用有效率、幻觉引用率与人工修改率，并保留 BM25、RRF 和可选 Rerank 的对比结果 |
| 兼容 | 现有 FFmpeg 粗剪和渲染能力继续通过自动测试 |

## 7. 产品边界

### 7.1 当前明确不做

- 自研完整多轨剪辑器。
- 以 MCP 或 Codex 操作剪辑软件作为核心卖点。
- AE Agent 或多个专业剪辑软件适配器。
- 完整手机剪辑功能和原生 App。
- 多机位同步、跨机位自动择镜和复杂专业后期；MVP 只支持将多段素材按上传顺序串接成一条源时间线。
- 无人工审核的全自动正式交付。
- 通用聊天机器人、通用企业知识库或与活动视频生产无关的 Agent 平台。

### 7.2 产品承诺

- 帮助非专业用户把剪辑要求表达清楚。
- 提高长素材中关键内容的发现和审核效率。
- 为重要候选提供可查看依据。
- 保存关键需求、修改和批准过程。
- 对可量化的成片要求进行确定性检查。

### 7.3 产品不承诺

- 自动保证人名、职务和奖项绝对正确。
- 自动理解所有无声画面。
- 替代专业剪辑师的创意判断。
- 一句话生成无需修改的最终成片。

## 8. 成功指标

MVP 不用主观“看起来好用”作为结论。以学校、企业各至少 3 个真实任务为一个验证批次，操作者先写下人工基准清单（必须环节、正确人名/奖项及原有流程耗时），再记录以下数据：

| 假设 | 首轮通过线 | 测量方式 |
| --- | --- | --- |
| 任务书能说清需求 | 操作者中位确认时间 ≤ 5 分钟；平均有效追问 ≤ 3 个；已明确槽位重复追问率 = 0 | 从提交原始需求到确认版本的审计时间、追问与槽位来源记录 |
| 能找到真正重要的内容 | 人工基准中的 `must` 环节，候选召回率 ≥ 90% | 基准清单中被候选覆盖的项目数 ÷ 总 `must` 项 |
| 证据不是伪造字段 | 证据引用有效率 ≥ 98%，幻觉引用率 = 0 | 引文原文、证据 ID 与时间范围均通过确定性校验的候选数 ÷ 总候选数 |
| 审核不会比剪映更累 | 审核者中位完成方案审核时间 ≤ 5 分钟 | 打开审核页到提交批准/修改的时间；不把观看素材时间计入 |
| 能减少返工 | 每任务平均重新导出 ≤ 1 次，且操作者主观确认“比原流程更容易说清需求” | 审计中的渲染版本数 + 任务后 5 分问卷 |

同时记录任务书修改率、候选接受/删除率、人工补片比例、字幕/人名/奖项修正次数和总耗时；它们用于解释指标，没有达到通过线时不得用“AI 很酷”替代原因分析。

## 9. 版本路线

### MVP 2：证据化 LLM 工作流闭环

- 学校/企业场景选择。
- 基于槽位状态的结构化任务书和有限多轮追问。
- 需求版本确认。
- 事件驱动的任务状态机、非法跳转保护和从本地任务产物恢复。
- 基于关键词和向量的转录证据检索。
- 受限 `search_evidence` 工具调用、候选原文引文和确定性引用校验。
- 电脑审核和基于标注集的召回、排序、引用与人工修改离线评测报告。
- 业务审计时间线。
- FFmpeg 成片和逐项验收报告。

### V1.1：降低返工（仅在 MVP 假设通过后启动）

- 在 MVP 本地状态恢复基础上，增加长任务断点续作、跨进程恢复和局部重新分析。
- 人物、职务、奖项专门确认流程。
- 活动流程表、主持稿、名单和产品资料等小规模辅助资料检索。
- 局域网手机审核链接、二维码、token、过期与撤销。
- 审核链接权限、过期和撤销。
- 云端低码率审核，原始素材本地保留。
- 组织品牌配置、专有名词词典、任务模板和可管理的组织记忆。

### V1.2：组织化生产（仅在 V1.1 有持续使用证据后启动）

- 学校和企业品牌模板。
- 多审核角色和审批状态。
- 横竖屏多版本输出。
- OCR、场景切换、音频事件和受限关键帧描述等多模态证据。
- 可替换的检索与 Rerank 后端；仅在数据规模和评测收益成立时引入服务化索引。
- 本地模型与云端模型可切换，在隐私、质量、延迟和成本上形成可复现实验。
- 真实素材评测集与质量统计。

### 外部执行器：暂不排期

Premiere、Resolve、After Effects 或其他工具适配不是路线承诺。只有当前述指标在至少两轮真实任务中达标，并且用户明确把“现有 FFmpeg 表达能力不足”列为主要阻碍时，才评估统一执行器接口；外部工具只负责时间线和渲染，需求、证据、批准和验收仍由映证管理。

## 10. 待验证假设

在继续扩大开发前，需用学校和企业各 3–5 个真实任务验证：

1. 长素材找重点、字幕核对和等待审核是否是高频痛点。
2. 用户是否愿意先确认结构化任务书再生成方案。
3. 可追溯证据是否能减少遗漏和返工。
4. 用户是否愿意为流程可靠性付费，而不只是为视觉效果付费。

**研发止损规则：** 在第一轮真实任务没有证明前 3 个假设和第 8 节前三项通过线之前，不启动 V1.1、组织模板、云端审核或任何外部剪辑软件适配；只修复妨碍验证当前假设的问题。
